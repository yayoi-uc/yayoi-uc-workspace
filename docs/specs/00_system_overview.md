## 1. プロジェクト概要

### 1.1 背景・目的
- ジュエリーD2Cブランド「ödül」（運営: Mhabit）
- インドで生産（リードタイム約3.5ヶ月）
- 手作業による業務工数を削減し、少人数でもスケーラブルな運営体制を構築する
- 5つの業務システムを段階的に開発・導入する

### 1.2 運営体制
| 役割 | 人数 | 備考 |
|------|------|------|
| メイン運営メンバー | 4名 | 全機能にアクセス |
| スタッフ（パート/アルバイト） | 変動 | 主に在庫管理の写真ログ・検品を担当 |

> 権限管理は将来的に導入予定。Phase 1では全員同じ権限で可。

### 1.3 現在の課題
| 業務領域 | 課題 |
|----------|------|
| 商品企画 | 発注数の決定が属人的、売上予測が感覚頼り |
| 企画書作成 | 毎回フォーマットが異なる、メーカーごとの対応が手間 |
| 生産管理 | 発注ステータスの把握が困難、リマインド漏れ |
| 在庫管理 | 検品・在庫数の管理がスプレッドシート頼り、OpenLogiへの連携が手動 |
| 分析 | 売上・在庫・広告データが分散、リオーダー判断が遅い |

#### A-0 リオーダー予測 詳細

**対象:** 定番商品・セミ定番商品のみ（アーカイブ商品は対象外）

**予測ロジック:**
- 過去の週次売上データから月間販売ペースを算出
- 現在庫 ÷ 月間販売ペース = 在庫切れまでの月数
- **3.5ヶ月（インド生産リードタイム）以内に0になるアイテムをアラート**

**商品分類別の扱い:**
| 分類 | リオーダーロジック |
|------|------------------|
| 定番商品 | 在庫切れ予測に基づき自動リオーダー提案。広告運用中のため欠品を避ける |
| セミ定番商品 | 在庫切れ予測 + 次回再販タイミング（半年/年1回）を加味。バリエーション追加の提案も含む |
| アーカイブ商品 | リオーダー対象外。ただしセミ定番への昇格提案はあり得る |

**イベント加味:**
- 年間イベントカレンダーを登録（バレンタイン、母の日、クリスマス、POPUPなど）
- 各イベントに**売上係数**を設定（例: 母の日 = 1.5x）
- POPUPイベントの場合は**売上目標金額**を直接入力可能
- イベント期間中の予測販売数 = 通常ペース × 係数

**リオーダーアラートレベル:**
| レベル | 条件 | アクション |
|--------|------|-----------|
| 要リオーダー | 在庫0予測が3.5ヶ月以内 | 発注手続きへ直行 |
| 注意 | 在庫0予測が3.5〜5ヶ月 | ウォッチリストに表示 |
| 余裕あり | 在庫0予測が5ヶ月以上 | 通常表示 |

**再販商品のリオーダー:**
- 過去販売数の1.2〜1.5倍が発注数の目安

#### A-1 新作発注計画 詳細

**フロー:**
1. シーズンを選択（PRE SS / SS / SS SUMMER / アニバーサリー&AW / ホリデー）
2. 企画分類ごとの型数を入力（デフォルト値は企画分類マスタから）
3. システムが発注数・期待売上を自動計算
4. 手修正可能 → 確定

**企画分類マスタの変数（発注計算に使用）:**
- 最大型数
- サイズ展開（リング: 9/11/13/15、その他: フリーサイズ等）
- 1サイズあたりの平均発注数
- 上限発注数
- 平均単価
- 90日以内の在庫消化率目安
- 最大ストーン数

> これらの変数は**暫定値**。売上データが蓄積されたら分析して更新する。
> システム上で変数を編集できるUIが必要。

**撮影スケジュール連動:**
- 新作発売にはクリエイティブ撮影が必須
- 発注計画作成時に、対応する撮影タイミングとコスト（50〜60万円/回）を表示
- 撮影日程を年間スケジュール（A-4）に反映

**毎週木曜発売の制約:**
- 発売日は必ず木曜日
- シーズン期間内の木曜日の数 = 最大発売回数
- 横転商品はシーズン開始2週目の木曜日に発売

> **未決定事項:**
> - [ ] 企画分類マスタの変数を売上分析後にどう更新するか（手動？自動提案？）

> - [ ] 発売順序のルール（流行品が先？横転商品が先？）

### C. 在庫管理システム

#### 目的
商品到着から検品・OpenLogi入庫までの一連のフローを管理する。

#### フロー（4ステップ）

```
(1) 到着分作成（社員）
    ↓
(2) 写真ログ（スタッフ）
    ↓
(3) 検品（社員/スタッフ）
    ↓
(4) ステータス管理
```

#### C-1 オフィス到着分 新規作成

| 項目 | 内容 |
|------|------|
| 操作者 | 社員 |
| 大カテゴリ | ○月○日到着分（到着日で分類） |
| 対象発注 | 生産管理DBの「Arrival」ステータスの発注から選択 |
| 自動処理 | 仕様確認（発注シート照合）、生産管理DBステータス更新、マスタ登録 |

#### C-2 写真アップロード＆文字起こしログ

| 項目 | 内容 |
|------|------|
| 操作者 | スタッフ（パート/アルバイト） |
| 入力 | 各袋の写真（複数枚同時アップロード可） |
| OCR対象 | 袋のラベル（品番、品名、数量、カラー等） |
| 手修正 | OCR精度が低い場合、全フィールドを手入力/修正可能 |
| 出力 | Excelダウンロード、到着アイテムのメーカー共有 |

#### C-3 検品

| 項目 | 内容 |
|------|------|
| 分類単位 | 大カテゴリ（到着日）→ 中カテゴリ（コレクション/現物BOX） |
| 結果入力 | 良品数、不良品数 |

**良品 → 出力:**
| 出力 | フォーマット |
|------|-------------|
| OpenLogi入庫CSV | OpenLogi規定フォーマット（要仕様確認） |
| シールプリント | 商品ラベル印刷（規定フォーマットあり、要共有） |

**不良品 → 別管理:**

| 項目 | 内容 |
|------|------|
| 不良分類（デフォルト） | キズ、クラック、仕様違い、石取れ |
| カスタム分類 | ユーザーが自由に追加可能 |
| 対応区分 | 交換 / 返品 / 交渉 |
| 交渉管理 | メモ欄（自由テキスト）で十分 |
| 写真 | 不良品ごとに写真添付 |

#### C-4 オフィス在庫ステータス管理

| 項目 | 内容 |
|------|------|
| 管理単位 | 中カテゴリ（コレクション）ごと |
| ステータス | 未到着 / 検品待ち / 一部入庫 / 入庫完了 |
| 表示項目 | 総数、オフィス在庫数、OpenLogi入庫済数、不良対応中数 |

> - [ ] OpenLogi CSVのフォーマット仕様書を共有してもらう

## 5. OEM商品企画DB（Phase 2）

Phase 1完了後に要件定義する。A.商品企画DBをベースに以下を追加予定:
- 取引先管理（契約書/契約内容/議事録Notionリンク）
- OEM固有の項目（MOQ、リードタイム、サンプル管理など）
- 発注フローの違い（承認ステップ等）

---

## 6. 技術スタック（案）

| レイヤー | 技術 | 理由 |
|---------|------|------|
| フロントエンド | Next.js (React) | Webダッシュボード、ödülブランドUI |
| バックエンド | Python (FastAPI) | データ処理・分析・OCRに強い |
| データベース | PostgreSQL | リレーショナルデータ管理 |
| インフラ | Vercel + Railway or Supabase | 少人数運用に最適、低コスト |
| ストレージ | S3互換（Supabase Storage等） | 検品写真の保存 |
| 外部連携 | Slack API, Google Sheets API | 通知、マスタ読み込み |
| OCR | Google Vision API（候補） | 袋ラベルの文字起こし |
| PDF生成 | WeasyPrint or ReportLab | 企画書PDF出力 |
| 認証 | Supabase Auth or NextAuth | 将来の権限管理に対応 |

## 7. データモデル（コアエンティティ）

```
Product（商品）
├── product_id (PK)
├── name
├── category (リング/ネックレス/ピアス/バングル/イヤリング/ブレスレット/チャーム等)
├── material (K10/SV925等)
├── color（地金カラー）
├── stone（ストーン種別）
├── cost_price（原価）
├── selling_price（販売価格）
├── supplier_id (FK)
├── sku
├── product_class（定番/セミ定番/アーカイブ/未分類）
├── size_options（サイズ展開。例: "9,11,13,15"）
├── launched_at（初回発売日）
├── launch_day_of_week（木曜日固定）
└── created_at
※ 正はGoogle Spreadsheetのマスタ。システムは定期同期。

ProductClass（商品分類）
├── product_class_id (PK)
├── product_id (FK)
├── class_type (staple / semi_staple / archive)
├── classified_at（分類日）
├── reason（分類理由メモ）
└── classified_by
※ 新作発売後に売上実績を見て振り分け。変更履歴を保持。

Season（シーズン）
├── season_id (PK)
├── name（PRE SS / SS / SS SUMMER / アニバーサリー&AW / ホリデー / 福袋）
├── year (2026等)
├── start_date
├── end_date
├── shooting_date（撮影日）
├── shooting_cost（撮影コスト。50〜60万円）
├── uses_previous_creative (boolean)（10月〜11月のようにクリエイティブ流用する場合）
└── notes

PlanningCategory（新作企画分類マスタ）
├── planning_category_id (PK)
├── name（流行品/テスト商品/改良品/横転商品セミ定番版/横転商品定番版/再販商品）
├── owner_role（ディレクター/MD）
├── is_new_product (boolean)
├── description（特徴）
├── max_styles（最大型数）
├── size_options（サイズ展開）
├── avg_order_per_size（1サイズあたり平均発注数）
├── max_order_quantity（上限発注数）
├── avg_unit_price（平均単価）
├── expected_sell_through_90d（90日以内の在庫消化率目安 %）
├── max_stones（最大ストーン数）
├── launch_timing_note（発売タイミング備考。例: "シーズン2週目"）
├── product_type_example（商品タイプ例）
└── updated_at
※ 暫定値。売上データ分析後に更新可能。

NewProductPlan（新作発注計画）
├── plan_id (PK)
├── season_id (FK)
├── planning_category_id (FK)
├── planned_styles（計画型数）
├── planned_quantity（計画発注数）
├── expected_revenue（期待売上）
├── launch_date（発売予定日。木曜日）
├── status (draft / confirmed / ordered)
└── created_by

Supplier（メーカー）
├── supplier_id (PK)
├── name
├── order_sheet_template（発注シートテンプレートID）
├── lead_time_days（リードタイム、デフォルト105日=3.5ヶ月）
└── contact_info

Order（発注）
├── order_id (PK)
├── product_id (FK)
├── supplier_id (FK)
├── season_id (FK)
├── planning_category_id (FK, nullable。新作の場合)
├── quantity
├── status（12段階: order_check_maker〜cancel）
├── status_updated_at
├── ordered_at
├── expected_delivery
├── actual_delivery
├── source_spreadsheet_url
├── is_oem (boolean)
└── is_reorder (boolean)

Event（イベント）
├── event_id (PK)
├── name（母の日、クリスマス、POPUP等）
├── start_date
├── end_date
├── sales_coefficient（売上係数。例: 1.5）
├── target_amount（POPUP等の売上目標金額。nullable）
└── type (seasonal / popup / campaign)

Arrival（到着分）
├── arrival_id (PK)
├── arrival_date
├── created_by
└── status (pending / inspecting / completed)

ArrivalItem（到着分-発注紐付け）
├── arrival_item_id (PK)
├── arrival_id (FK)
├── order_id (FK)
└── quantity_expected

PhotoLog（写真ログ）
├── photo_log_id (PK)
├── arrival_item_id (FK)
├── bag_number
├── photo_url
├── ocr_product_code
├── ocr_product_name
├── ocr_quantity
├── ocr_color
├── manual_override (boolean)
└── created_at

Inspection（検品）
├── inspection_id (PK)
├── arrival_item_id (FK)
├── quantity_good
├── quantity_defective
├── inspected_at
└── inspected_by

Defect（不良品）
├── defect_id (PK)
├── inspection_id (FK)
├── defect_type（キズ/クラック/仕様違い/石取れ/カスタム）
├── quantity
├── photo_url
├── action（交換/返品/交渉）
├── action_status（未対応/対応中/完了）
├── memo（交渉メモ等）
└── created_at

DefectType（不良品分類マスタ）
├── defect_type_id (PK)
├── name（キズ、クラック、仕様違い、石取れ）
└── is_custom (boolean)
※ デフォルト4種 + ユーザー追加可能

Sales（売上）
├── sale_id (PK)
├── product_id (FK)
├── quantity
├── revenue
├── channel（shopify / elle）
├── sold_at
└── imported_at

AdSpend（広告費）
├── ad_spend_id (PK)
├── date
├── platform (meta)
├── spend
├── impressions
├── clicks
└── imported_at

InventoryStatus（オフィス在庫ステータス）
├── inventory_status_id (PK)
├── arrival_item_id (FK)
├── total_quantity
├── office_quantity
├── openlogi_quantity
├── defect_quantity
├── status (awaiting / pending_inspection / partial / stored)
└── updated_at
```

| 項目 | 要件 |
|------|------|
| 可用性 | 99%（小規模運用） |
