## 1. プロジェクト概要

### 1.1 背景・目的
- ジュエリーD2Cブランド「ödül」（運営: Mhabit）
- インドで生産（リードタイム約3.5ヶ月）
- 手作業による業務工数を削減し、少人数でもスケーラブルな運営体制を構築する
- 5つの業務システムを段階的に開発・導入する

### 1.2 運営体制
| 役割 | 人数 | 備考 |
|------|------|------|
| メイン運営メンバー | 4名 | 全機能にアクセス |
| スタッフ（パート/アルバイト） | 変動 | 主に在庫管理の写真ログ・検品を担当 |

> 権限管理は将来的に導入予定。Phase 1では全員同じ権限で可。

### 1.3 現在の課題
| 業務領域 | 課題 |
|----------|------|
| 商品企画 | 発注数の決定が属人的、売上予測が感覚頼り |
| 企画書作成 | 毎回フォーマットが異なる、メーカーごとの対応が手間 |
| 生産管理 | 発注ステータスの把握が困難、リマインド漏れ |
| 在庫管理 | 検品・在庫数の管理がスプレッドシート頼り、OpenLogiへの連携が手動 |
| 分析 | 売上・在庫・広告データが分散、リオーダー判断が遅い |

## 4. システム別 要件定義

### A. 商品企画DB

#### 目的
売上データに基づいてリオーダーと新規発注の意思決定を支援する。

#### 機能一覧

| # | 機能 | 概要 | 入力 | 出力 |
|---|------|------|------|------|
| A-0 | リオーダー数決定 | 在庫が0になる時期を予測し、リオーダーを提案 | 売上データ、現在庫、イベント情報 | リオーダーアラート一覧 |
| A-1 | 発注数決定 | 販売期間・売上目標からカテゴリ別の発注数を算出 | 販売期間、売上目標、原価率 | カテゴリ別発注計画（手修正可） |
| A-2 | 企画書作成 | シーズン企画内容を企画書として自動生成 | A-1の結果 + 自由テキスト | PDF / PNG |
| A-3 | 発注シート出力 | メーカー別フォーマットで発注シートを生成 | 発注計画 + メーカー選択 | Excel / クリップボード |

#### A-0 リオーダー予測 詳細

**予測ロジック:**
- 過去の週次売上データから月間販売ペースを算出
- 現在庫 ÷ 月間販売ペース = 在庫切れまでの月数
- **3.5ヶ月（インド生産リードタイム）以内に0になるアイテムをアラート**

**イベント加味:**
- 年間イベントカレンダーを登録（バレンタイン、母の日、クリスマス、POPUPなど）
- 各イベントに**売上係数**を設定（例: 母の日 = 1.5x）
- POPUPイベントの場合は**売上目標金額**を直接入力可能
- イベント期間中の予測販売数 = 通常ペース × 係数

**リオーダーアラートレベル:**
| レベル | 条件 | アクション |
|--------|------|-----------|
| 要リオーダー | 在庫0予測が3.5ヶ月以内 | 発注手続きへ直行 |
| 注意 | 在庫0予測が3.5〜5ヶ月 | ウォッチリストに表示 |
| 余裕あり | 在庫0予測が5ヶ月以上 | 通常表示 |

> **未決定事項:**
> - [ ] イベント係数のデフォルト値を決める
> - [ ] リオーダー提案数の算出ロジック（何ヶ月分を発注するか）
> - [ ] 季節性の考慮（単純線形 or 季節補正あり）

#### A-3 発注シート 詳細

**メーカー管理:**
- 現在3社。今後増加の可能性あり
- 各メーカーごとに発注シートフォーマットが異なる
- フォーマットはシステム内でテンプレートとして管理
- 新規メーカー追加時にテンプレートを登録できる

**出力形式:**
- Excel ダウンロード
- クリップボードコピー（既存スプレッドシートへの貼り付け用）

> **未決定事項:**
> - [ ] 各メーカーのフォーマット仕様を共有してもらう（3社分）
> - [ ] メーカーテンプレートの登録UIは必要か？（管理者のみ？）

### B. 生産管理DB

#### 目的
発注から到着までの全工程を可視化し、遅延を早期検知する。

#### データソース
- **Google Spreadsheet（各社発注シート）を自動読み込み**
- A.商品企画DBの発注データとも連携

#### 生産ステータス（全12段階）

| # | ステータス | 担当 | 説明 |
|---|-----------|------|------|
| 1 | Order Check | Maker | メーカーが発注内容を確認中 |
| 2 | Stone Check | Maker | 石の確認・選定中 |
| 3 | Stone Cancel | ödül | 石のキャンセル（ödül判断） |
| 4 | Design Check | Maker | デザイン確認中 |
| 5 | Sample Making | Maker | サンプル製作中 |
| 6 | Sample Check | ödül | サンプルをödülが確認 |
| 7 | Item Making | Maker | 本生産中 |
| 8 | Item Check | ödül | 完成品をödülが確認 |
| 9 | Delivery | - | 配送中（インド→日本） |
| 10 | Arrival | ödül | 到着済み（→在庫管理へ） |
| 11 | Cancel | ödül | キャンセル（ödül判断） |
| 12 | Order Check | ödül | ödül側の発注確認 |

> **補足:** Maker側のステータスはメーカーからの報告をödül側が手動更新する想定。
> 将来的にメーカー向けポータルを検討する可能性あり。

#### Slackアラート

| トリガー | 通知内容 | 通知先 |
|----------|----------|--------|
| 遅延検知 | 「{商品名}が{X日}遅延しています」 | 社内Slackチャンネル（固定） |

> **未決定事項:**
> - [ ] 遅延の定義（各ステータスに期待日数を設定？納品予定日との比較？）
> - [ ] 通知先のSlackチャンネル名
> - [ ] 遅延以外の通知は不要？（到着時、ステータス変更時など）
> - [ ] メーカーからのステータス更新方法（メール→手動入力？）

### C. 在庫管理システム

#### 目的
商品到着から検品・OpenLogi入庫までの一連のフローを管理する。

#### フロー（4ステップ）

```
(1) 到着分作成（社員）
    ↓
(2) 写真ログ（スタッフ）
    ↓
(3) 検品（社員/スタッフ）
    ↓
(4) ステータス管理
```

#### C-1 オフィス到着分 新規作成

| 項目 | 内容 |
|------|------|
| 操作者 | 社員 |
| 大カテゴリ | ○月○日到着分（到着日で分類） |
| 対象発注 | 生産管理DBの「Arrival」ステータスの発注から選択 |
| 自動処理 | 仕様確認（発注シート照合）、生産管理DBステータス更新、マスタ登録 |

#### C-2 写真アップロード＆文字起こしログ

| 項目 | 内容 |
|------|------|
| 操作者 | スタッフ（パート/アルバイト） |
| 入力 | 各袋の写真（複数枚同時アップロード可） |
| OCR対象 | 袋のラベル（品番、品名、数量、カラー等） |
| 手修正 | OCR精度が低い場合、全フィールドを手入力/修正可能 |
| 出力 | Excelダウンロード、到着アイテムのメーカー共有 |

#### C-3 検品

| 項目 | 内容 |
|------|------|
| 分類単位 | 大カテゴリ（到着日）→ 中カテゴリ（コレクション/現物BOX） |
| 結果入力 | 良品数、不良品数 |

**良品 → 出力:**
| 出力 | フォーマット |
|------|-------------|
| OpenLogi入庫CSV | OpenLogi規定フォーマット（要仕様確認） |
| シールプリント | 商品ラベル印刷（規定フォーマットあり、要共有） |

**不良品 → 別管理:**

| 項目 | 内容 |
|------|------|
| 不良分類（デフォルト） | キズ、クラック、仕様違い、石取れ |
| カスタム分類 | ユーザーが自由に追加可能 |
| 対応区分 | 交換 / 返品 / 交渉 |
| 交渉管理 | メモ欄（自由テキスト）で十分 |
| 写真 | 不良品ごとに写真添付 |

#### C-4 オフィス在庫ステータス管理

| 項目 | 内容 |
|------|------|
| 管理単位 | 中カテゴリ（コレクション）ごと |
| ステータス | 未到着 / 検品待ち / 一部入庫 / 入庫完了 |
| 表示項目 | 総数、オフィス在庫数、OpenLogi入庫済数、不良対応中数 |

> **未決定事項:**
> - [ ] OpenLogi CSVのフォーマット仕様書を共有してもらう
> - [ ] 商品ラベル（シールプリント）のフォーマットを共有してもらう
> - [ ] 商品マスタのスプレッドシート列定義を確認する
> - [ ] OCRの技術選定（Google Vision API? 等）
> - [ ] 写真の保存先・容量（S3等のストレージ）

### D. Mhabit ダッシュボード

#### 目的
売上・在庫・広告データを統合し、リオーダー判断を支援する。

#### 機能一覧

| # | 機能 | 概要 |
|---|------|------|
| D-1 | 売上ダッシュボード | 売上KPI、月別推移、カテゴリ別、TOP商品を一目で確認 |
| D-2 | 在庫消化率分析 | 商品別の消化率、在庫0予測日、月販ペースを一覧表示 |
| D-3 | リオーダー提案 | D-2の分析結果から自動でリオーダー候補を生成 → A.商品企画DBに自動反映 |

#### D-1 売上ダッシュボード

**データソース:**
| ソース | データ | 取込方法 |
|--------|--------|----------|
| Shopify | 自社EC売上 | CSV手動インポート（週次） |
| ELLE | ELLE経由売上 | CSV手動インポート（週次） |
| Meta | 広告費・ROAS | 未定 |

**KPI表示:**
- 売上合計（期間切替: 月/四半期/半年/年）
- 広告費 & ROAS
- 粗利 & 粗利率
- 在庫金額 & 消化率

**チャート:**
- 月別売上推移
- カテゴリ別売上比率
- 売上TOP 5商品

#### D-3 リオーダー提案 → 商品企画DB連携

**連携方法:** 自動反映
- ダッシュボードの分析結果（消化率、月販ペース、在庫0予測日）をA.商品企画DBの変数として自動連携
- A-0 リオーダー予測のインプットデータとなる

> **未決定事項:**
> - [ ] Meta広告データの取込方法（API連携 or CSV手動?）
> - [ ] ShopifyのCSVフォーマット確認（どの項目をインポートするか）
> - [ ] ELLEのCSVフォーマット確認
> - [ ] 統合ロジック（Shopify + ELLEの売上を商品単位で合算する方法）

## 6. 技術スタック（案）

| レイヤー | 技術 | 理由 |
|---------|------|------|
| フロントエンド | Next.js (React) | Webダッシュボード、ödülブランドUI |
| バックエンド | Python (FastAPI) | データ処理・分析・OCRに強い |
| データベース | PostgreSQL | リレーショナルデータ管理 |
| インフラ | Vercel + Railway or Supabase | 少人数運用に最適、低コスト |
| ストレージ | S3互換（Supabase Storage等） | 検品写真の保存 |
| 外部連携 | Slack API, Google Sheets API | 通知、マスタ読み込み |
| OCR | Google Vision API（候補） | 袋ラベルの文字起こし |
| PDF生成 | WeasyPrint or ReportLab | 企画書PDF出力 |
| 認証 | Supabase Auth or NextAuth | 将来の権限管理に対応 |

## 7. データモデル（コアエンティティ）

```

├── name

Order（発注）

├── supplier_id (FK)

├── status（12段階: order_check_maker〜cancel）
├── status_updated_at
├── ordered_at
├── expected_delivery

├── source_spreadsheet_url

Event（イベント）
├── event_id (PK)
├── name（母の日、クリスマス、POPUP等）

├── end_date
├── sales_coefficient（売上係数。例: 1.5）
├── target_amount（POPUP等の売上目標金額。nullabletext）

Arrival（到着分）
├── arrival_id (PK)

├── created_by

ArrivalItem（到着分-発注紐付け）
├── arrival_item_id (PK)

PhotoLog（写真ログ）
├── photo_log_id (PK)

├── photo_url

Inspection（検品）

Defect（不良品）
```
