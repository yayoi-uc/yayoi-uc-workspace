## 1. プロジェクト概要

### 1.1 背景・目的
- ジュエリーD2Cブランド「Maison TOI」を3名体制で運営
- 手作業による業務工数を削減し、少人数でもスケーラブルな運営体制を構築する
- 5つの業務システムを段階的に開発・導入する

### 1.2 運営体制
| 役割 | 人数 | 備考 |
|------|------|------|
| 運営メンバー | 3名 | 全員がシステム利用者 |

### 1.3 現在の課題
| 業務領域 | 課題 |
|----------|------|
| 商品企画 | 発注数の決定が属人的、売上予測が感覚頼り |
| 企画書作成 | 毎回フォーマットが異なる、メーカーごとの対応が手間 |
| 生産管理 | 発注ステータスの把握が困難、リマインド漏れ |
| 在庫管理 | 検品・在庫数の管理がスプレッドシート頼り、OpenLogiへの連携が手動 |
| 分析 | 売上・在庫・広告データが分散、リオーダー判断が遅い |

### 2.1 開発対象ツール一覧

|---|---------|---------|--------|
| 1 | 商品企画DB | 発注数決定・売上シミュレーション・発注シート自動出力 | TBD |

   │    │    │    │    │
   ▼    ▼    ▼    ▼    ▼
  ①   ②   ③   ④   ⑤    ← 各ツールモジュール
               │    │
               ▼    ▼

### 2.3 データフロー（ツール間連携）

```
① 商品企画DB ──→ ② 企画書フォーマット（商品情報を引用）
     │
     ▼
③ 生産管理 ←──── 発注データ
     │
     ▼
④ 在庫管理 ←──── 入荷データ ──→ OpenLogi
     │
     ▼

     │
     ▼

```

## 3. 技術スタック（案）

| レイヤー | 技術 | 理由 |
|---------|------|------|
| フロントエンド | Next.js (React) | 3名で使えるWebダッシュボード |
| バックエンド | Python (FastAPI) | データ処理・分析に強い |
| データベース | PostgreSQL | リレーショナルデータ管理 |
| インフラ | Vercel + Railway or Supabase | 少人数運用に最適、低コスト |
| 外部連携 | Slack API, OpenLogi API | 既存ツールとの連携 |
| PDF生成 | WeasyPrint or ReportLab | 企画書PDF出力用 |
| 認証 | Supabase Auth or NextAuth | シンプルな認証 |

## 4. 共通設計方針

### 4.1 設計原則
- **シンプルさ優先**: 3人で運用できる複雑さに抑える
- **段階的開発**: 1ツールずつ開発・リリース
- **データ連携重視**: ツール間でデータを共有するDB設計
- **自動化**: 手作業の繰り返しタスクは自動化する

### 4.2 共通データモデル（コアエンティティ）

```
Product（商品）
├── product_id (PK)
├── name
├── category
├── material
├── cost_price（原価）
├── selling_price（販売価格）
├── supplier_id (FK)
└── created_at

Supplier（メーカー/仕入先）
├── supplier_id (PK)
├── name
├── contact_info
├── lead_time_days（リードタイム）
└── payment_terms

Order（発注）
├── order_id (PK)
├── product_id (FK)
├── supplier_id (FK)
├── quantity
├── status（発注済/製造中/出荷済/入荷済/検品済）
├── ordered_at
├── expected_delivery
└── actual_delivery

Inventory（在庫）
├── inventory_id (PK)
├── product_id (FK)
├── quantity_good（良品数）
├── quantity_defective（不良品数）
├── location（保管場所）
└── updated_at

Sales（売上）
├── sale_id (PK)
├── product_id (FK)
├── quantity
├── revenue
├── channel（販売チャネル）
├── sold_at
└── ad_cost（広告費）
```

### 4.3 非機能要件
| 項目 | 要件 |
|------|------|
| 可用性 | 99%（小規模運用のため） |
| 同時接続 | 最大3名 |
| レスポンス | 画面表示 2秒以内 |
| データ保持 | 最低3年間 |
| バックアップ | 日次自動バックアップ |
| セキュリティ | HTTPS、認証必須、個人情報暗号化 |

## 5. 開発ロードマップ（案）

### 5.1 フェーズ分け

```
Phase 1: 基盤構築 + 最優先ツール
  ├── 共通DB・認証基盤
  └── 優先度1のツール

Phase 2: 業務効率化ツール群
  └── 優先度2-3のツール

Phase 3: 分析・最適化
  └── 残りのツール + ツール間連携強化
```

### 5.2 優先度の決め方
以下の基準で優先度を決定する：

| 基準 | 重み | 説明 |
|------|------|------|
| 工数削減インパクト | 高 | 現状どれだけ手間がかかっているか |
| 他ツールへの依存 | 高 | 他ツールの前提となるデータを持つか |
| 開発の容易さ | 中 | 早く成果を出せるか |
| 緊急度 | 中 | 今すぐ必要か |

## 付録: 用語集

| 用語 | 説明 |
|------|------|
| D2C | Direct to Consumer。自社で企画・製造・販売を一貫して行うビジネスモデル |
| OpenLogi | 物流アウトソーシングサービス。在庫保管・出荷代行 |
| リードタイム | 発注から納品までの所要期間 |
| リオーダー | 追加発注。売れ行きに応じて在庫を補充する |
| SKU | Stock Keeping Unit。在庫管理の最小単位 |
