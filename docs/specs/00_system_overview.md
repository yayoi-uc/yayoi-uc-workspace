## 1. プロジェクト概要

### 1.1 背景・目的
- ジュエリーD2Cブランド「ödül」（運営: Mhabit）
- インドで生産（リードタイム約3.5ヶ月）
- 手作業による業務工数を削減し、少人数でもスケーラブルな運営体制を構築する
- 商品企画・生産管理・在庫管理・分析を統合した1つのWebシステム

### 1.2 運営体制
| 役割 | 人数 | 備考 |
|------|------|------|
| メイン運営メンバー | 4名 | 全機能にアクセス |
| スタッフ（パート/アルバイト） | 変動 | 主に在庫管理の検品を担当 |

> 権限管理は将来的に導入予定。現時点では全員同じ権限（パスワード認証のみ）。

### 1.3 解決した課題
| 業務領域 | 旧課題 | 解決方法 |
|----------|--------|----------|
| 商品企画 | 発注数の決定が属人的 | リオーダーアラート自動計算（加重移動平均+イベント係数） |
| 企画書作成 | フォーマットが不統一 | テンプレート機能+PDF出力 |
| 生産管理 | ステータスの把握が困難 | 12段階カンバンビュー+Slack通知 |
| 在庫管理 | スプレッドシート頼り | 在庫管理画面+OpenLogi連携+検品管理 |
| 分析 | データが分散 | 統合ダッシュボード（6種類の分析ビュー） |

## 2. システム構成

### 2.1 技術スタック（確定）

| レイヤー | 技術 | 理由 |
|---------|------|------|
| フロントエンド + API | Next.js 16 (App Router) | フルスタック一本化、Vercelとの親和性 |
| データベース | Supabase (PostgreSQL) | Free tier、RLS対応、Storage付き |
| ホスティング | Vercel Hobby plan | 無料、Cron Jobs付き |
| 認証 | Cookie-based パスワード認証 | シンプル、小規模チーム向け |
| Excel出力 | exceljs | 発注シートExcel出力 |
| PDF生成 | @react-pdf/renderer | 企画書PDF出力 |
| ストレージ | Supabase Storage | 検品写真の保存 |
| 外部連携 | Slack Webhook, Google Sheets API, Shopify API, OpenLogi API | 通知・同期 |

> **月額コスト: $0**（全サービス無料枠内で運用）

### 2.3 外部連携

| サービス | 連携方法 | 用途 | ステータス |
|----------|----------|------|-----------|
| Shopify | REST API | 商品同期・在庫同期 | 実装済み |
| OpenLogi | REST API | 在庫数同期・CSV出力 | 実装済み |
| Google Sheets | API (読み取り専用) | 商品マスタ同期 | 実装済み |

| ELLE | CSV手動インポート | 売上取込 | 実装済み |
| Meta広告 | CSV手動インポート | 広告費データ取込 | 実装済み |

### 2.4 セキュリティ方針

**3原則:**
1. **個人情報を持たない** — DBに顧客テーブルなし。APIからも顧客情報を取得しない
2. **書き込み権限を持たない** — 外部API連携は読み取り専用（Shopify/OpenLogi/Sheets）
3. **Meta APIトークンを持たない** — 乗っ取りリスク対策。広告データはCSVインポート

**実装済みセキュリティ:**
- パスワード保護（全ページ。Cookie認証、30日有効）
- Supabase RLS有効化（全22テーブル）
- サーバーサイドのみservice_role_keyを使用
- Cron APIはCRON_SECRETで保護
- 機密情報は環境変数管理（Vercel）

## 4. リオーダーアラート 計算ロジック（実装済み）

**対象:** 定番商品・セミ定番商品

**計算手法:**
1. 過去12週間の売上データを取得
2. 週別バケットに分割（直近4週 / 古い8週）
3. **加重移動平均**: 直近4週 × 0.7 + 古い8週 × 0.3 → 週次販売ペース
4. 月次販売ペース = 週次 × 4.33 × イベント係数
5. 有効在庫 = 現在庫 + 発注中の入荷予定在庫
6. 在庫切れ予測月数 = 有効在庫 ÷ 月次販売ペース

**アラートレベル:**
| レベル | 条件 | 意味 |
|--------|------|------|
| Critical（要リオーダー） | 在庫切れ ≤ リードタイム | 今すぐ発注しないと欠品 |
| Warning（注意） | 在庫切れ ≤ リードタイム + バッファ(1.5ヶ月) | そろそろ発注準備 |
| Safe（余裕あり） | それ以上 | 当面OK |

**推奨発注数の算出:**
- 安全在庫 = max(5個, 月次販売ペース × 0.5)
- 目標在庫 = 安全在庫 + 月次販売ペース × (リードタイム + バッファ)
- 推奨数 = ceil((目標在庫 - 有効在庫) × 再販倍率) → 5個単位に切り上げ

**再販倍率（セミ定番のみ）:**
| 前回90日消化率 | 発注倍率 |
|---------------|---------|
| 80%以上 | 1.5倍 |
| 60〜80% | 1.3倍 |
| 40〜60% | 1.2倍 |
| 40%未満 | 1.0倍 |

## 5. 生産管理 ステータスフロー（実装済み）

**12段階:**
```
企画中 → 発注準備 → 発注済 → 素材調達中 → 製造中 → 仕上げ → 品質検査 → 出荷準備 → 輸送中 → 通関 → 国内配送 → 完了
```

- ステータス変更時にSlack通知
- 変更履歴・コメント記録
- 「国内配送」到達で actual_delivery 自動セット
- 「完了」到達で検品対象に

## 6. 商品分類ルール（実装済み）

**2段階判定:**
| 段階 | タイミング | 判定基準（デフォルト） |
|------|-----------|----------------------|
| 仮分類 | 発売後7日 | 定番候補: ≥5個販売、アーカイブ候補: ≤1個販売 |
| 本分類 | 発売後90日 | 定番: ≥70%消化率、アーカイブ: <40%消化率 |

- 閾値は設定画面で変更可能
- 手動分類変更可能（履歴保持）
- システム提案 + 手動確定のフロー

## 7. 自動処理（Cron）

### Daily (毎日 21:00 UTC = 翌朝6:00 JST)
1. OpenLogi在庫数同期
2. リオーダーアラート再計算 → Critical時にSlack通知
3. 納期間近（3日以内）の発注リマインダー → Slack通知
4. 納期超過チェック

### Weekly (毎週金曜)
1. Shopify vendorフィールドから商品分類同期
2. Shopify在庫数同期
3. リオーダーアラート再計算
4. 納期間近（7日以内）の発注リマインダー → Slack通知
5. 週次サマリー → Slack通知（売上/アラート/発注状況）
