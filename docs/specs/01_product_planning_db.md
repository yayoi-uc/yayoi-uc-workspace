**作成日:** 2026-04-09
**更新日:** 2026-05-11
**ステータス:** 実装完了 (Beta v1.0)
**開発優先度:** Phase 1（最優先）— 全機能実装済み

---

## 1. 概要

### 1.1 目的
売上データと商品分類ルールに基づき、リオーダーと新作の発注意思決定を支援する。
Google Spreadsheetの商品マスタを正とし、売上・在庫データを組み合わせて定量的な発注判断を提供する。

### 1.2 解決する課題
| 現状の課題 | システムで解決 |
|-----------|--------------|
| 発注数を感覚で決めている | 過去売上データ + 消化率分析で算出 |
| 商品分類（定番/セミ定番/アーカイブ）が属人判断 | 7日仮分類 + 90日確定判定を自動提案 |
| リオーダーのタイミングを見逃す | 在庫切れ予測 + 3.5ヶ月リードタイム逆算でアラート |
| 発注シートを毎回手作業で作成 | メーカー別テンプレートで自動生成 |
| 新作の企画変数がブレる | 企画分類マスタで標準値を管理、実績ベースで自動提案 |

### 1.3 ユーザーストーリー
- **MDとして**、定番商品の在庫切れを3.5ヶ月前に検知し、リオーダー判断をしたい
- **MDとして**、新作の企画分類に応じた発注数・期待売上を自動計算してほしい
- **ディレクターとして**、シーズンの企画書を素早く作成したい
- **MDとして**、新商品を7日後に自動分類し、90日後に確定分類したい
- **運営メンバーとして**、メーカー別の発注シートをワンクリックで出力したい

## 6. ビジネスロジック

### 6.1 リオーダー予測（A-0）

```
■ データソース
  現在庫数: OpenLogi API → items/{id}?stock=1 → available（利用可能数）
  売上データ: Shopify API → 注文のSKU・数量・日時（個人情報は取得しない）
           + ELLE CSV → 週次手動インポート

■ 月間販売ペース算出
  monthly_rate = (Shopify売上 + ELLE売上) の過去12週平均 × 4.33
  ※ 発売12週未満の場合は、あるデータ全てを使用

■ 在庫切れ予測
  months_until_stockout = OpenLogi在庫数(available) / monthly_rate

■ アラートレベル判定
  if months_until_stockout ≤ 3.5:  critical（要リオーダー）
  if months_until_stockout ≤ 5.0:  warning（注意）
  else:                             safe（余裕あり）

■ 推奨発注数（定番商品）
  target_stock = safety_stock + (monthly_rate × 5)  ← 5ヶ月分（3.5ヶ月リードタイム+1.5ヶ月バッファ）
  recommended = max(0, target_stock - current_stock)

■ 推奨発注数（セミ定番商品）
  resale_plans テーブルから次回再販予定月を参照
  order_deadline = planned_month − 105日（3.5ヶ月リードタイム）
  recommended = previous_order_quantity × restock_multiplier
  ※ quantity_override が設定されていればそちらを優先
  ※ resale_plansに予定がないセミ定番は、アラート一覧で「再販予定未登録」と表示

■ イベント加味
  イベント期間と重なる場合:
  adjusted_monthly_rate = monthly_rate × event.sales_coefficient
  推奨数もイベント係数で補正
```

### 6.2 商品分類判定（A-2）

```
■ 7日一次判定（自動トリガー: 毎日バッチ）
  対象: launched_at + 7日 が今日以前 & product_class = '未分類'

  初週販売数 = SUM(sales WHERE sold_at BETWEEN launched_at AND launched_at + 7)

  if 初週販売数 >= thresholds.preliminary.staple_min:
    suggestion = '定番候補'
  elif 初週販売数 <= thresholds.preliminary.archive_max:
    suggestion = 'アーカイブ候補'
  else:
    suggestion = 'セミ定番候補'

  → 通知を発出。ユーザーが承認 or 変更して確定。

■ 90日確定判定（自動トリガー: 毎日バッチ）
  対象: launched_at + 90日 が今日以前 & product_class_stage = 'preliminary'

  消化率 = SUM(sales_quantity) / initial_order_quantity × 100

  if 消化率 >= thresholds.confirmed.staple_min:
    suggestion = '定番'
  elif 消化率 < thresholds.confirmed.archive_max:
    suggestion = 'アーカイブ'
  else:
    suggestion = 'セミ定番'

  → 通知を発出。ユーザーが承認 or 変更して確定。
```

### 6.3 新作発注計画（A-1）

```
■ 発注数算出
  企画分類マスタの値を使用:
  base_quantity = planned_styles × size_options_count × avg_order_per_size

  if max_order_quantity is set:
    quantity = min(base_quantity, max_order_quantity)

■ 期待売上
  expected_revenue = quantity × avg_unit_price × expected_sell_through_90d / 100

■ 再販商品の場合
  前回発注数 × restock_multiplier(前回90日消化率に基づく)

■ 横転商品の発売タイミング
  launch_date = season.start_date の翌週木曜日（シーズン2週目）
```

### 6.4 発注シート出力（A-4）

```
■ メーカー別テンプレート
  supplier.order_sheet_template_id に基づきフォーマットを選択

  取引先1（abi）: 約57列 + 検品管理列、石最大5セット、価格INR
  取引先2（shrma）: 約57列、石最大3セット、価格INR+JPY併記
  取引先3: 約57列、石最大3セット

■ 列マッピング
  products テーブルの値をテンプレートの各列にマッピング
  ※ 空列は空白のまま出力（メーカー側で記入する列がある）

■ 出力
  openpyxl等でExcel生成 → ダウンロード
  or クリップボードフォーマット（TSV）で出力
```

### 6.5 Spreadsheet同期（A-6）

```
■ 同期方式
  Google Sheets API v4 でデータ取得
  SKU列をキーにUPSERT

■ 同期スケジュール
  - 定期: 1日1回（深夜バッチ）
  - 手動: 管理画面から「今すぐ同期」ボタン

■ 同期対象列（80列中、システムが使用する列のみ）
  - SKU, 商品名, 英語名, カテゴリ, 素材, カラー
  - ストーン1〜3, 原価INR, 為替レート, 原価JPY, 販売価格
  - サイズ展開, メーカー名

■ 差分検出
  synced_at と Spreadsheet更新日時を比較
  変更があった行のみ更新

■ 注意
  Spreadsheetが正。システム上での商品マスタ直接編集は不可。
  分類(product_class)はシステム側で管理（Spreadsheetとは別管理）。
```

### 6.6 企画分類マスタ自動提案（A-7）

```
■ 提案ロジック
  対象: 各企画分類（流行品、テスト商品等）の発注変数

  過去の同分類商品の実績を集計:
  - 実績平均発注数
  - 実績消化率
  - 実績売上平均

  現行値との差分を表示:
  「消化率目安: 65% → 実績平均 72%（+7pt）」

■ トリガー
  90日確定判定のバッチ後に、該当分類の実績を再集計

■ 適用
  ユーザーが「提案を適用」ボタンで更新
  or 手動で任意の値に修正
```

### 8.1 データ取得ポリシー（個人情報保護）

**原則: 本システムは個人情報を一切取得・保存しない。**

| 連携先 | 取得する | 取得しない |
|-------|---------|-----------|
| OpenLogi API | 商品ID・SKU・在庫数量 | 顧客名・配送先・注文者情報 |
| Shopify API | 商品SKU・販売数量・販売日時・売上金額 | 顧客名・メールアドレス・電話番号・住所・決済情報 |
| ELLE CSV | 商品コード・販売数量・販売日時・売上金額 | 顧客に関する一切の情報（※ CSVに個人情報列なし。確認済み） |

**実装ルール:**
- Shopify APIはフィールド指定で商品・売上関連項目のみ取得する
- DBに顧客テーブルは作成しない
- ログにも個人情報が混入しないよう、APIレスポンスの生データは保存しない
- CSVインポート時にも個人情報列があれば取り込み対象外とする

### 8.2 セキュリティ設計（サードパーティ連携リスク対策）

#### リスク一覧と対策

**リスク①: アカウント乗っ取り（APIトークン漏洩経由）**

万が一APIトークンが漏洩した場合の被害範囲を最小化する。

| 連携先 | 権限設定 | 最悪ケースの被害範囲 |
|-------|---------|-------------------|
| OpenLogi | **読み取り専用トークン**を使用。出荷・入荷操作の権限を付与しない | 在庫数が見られるだけ。出荷・金銭操作は不可 |
| Shopify | **read_orders, read_products のみ**のPrivate App。write権限・顧客情報権限を一切付与しない | 商品と注文件数が見られるだけ。商品変更・決済操作・顧客情報閲覧は不可 |
| Google Sheets | **読み取り専用**のサービスアカウント。編集権限を付与しない | スプレッドシートが見られるだけ。データ改ざん不可 |
| Slack | **Incoming Webhook のみ**。Bot Tokenは使わない | 特定チャンネルへの投稿のみ。メッセージ閲覧・チャンネル操作は不可 |

**実装ルール:**
- 全APIトークンは**環境変数**で管理（コードにハードコーディングしない）
- トークンは**Vercel/Railway等のシークレット管理**機能で暗号化保存
- 各サービスで**最小権限の原則**を厳守（読み取りのみ、必要なスコープのみ）
- APIトークンの**定期ローテーション**（3ヶ月ごと）をスケジュール化

**リスク②: 金銭的被害**

| 脅威 | 対策 |
|------|------|
| Shopify経由で不正注文・価格変更 | write権限を付与しないため**原理的に不可能** |
| OpenLogi経由で不正出荷 | 出荷APIの権限を付与しないため**原理的に不可能** |
| API利用料の暴走 | OpenLogi: 60リクエスト/分の制限あり。システム側でも日次1回に制限。Shopify: APIコール数をモニタリング |
| サードパーティ側の料金変更 | API利用は全サービス無料。有料化された場合はCSV代替に切り替え可能な設計 |

**リスク③: 顧客情報漏洩**

| 脅威 | 対策 |
|------|------|
| Shopify APIから顧客情報が取得される | **取得フィールドを限定**。顧客関連スコープ(read_customers)を付与しない。APIレスポンスに顧客情報が含まれない |
| DBから顧客情報が流出 | **DBに顧客テーブルが存在しない**。保存していないので漏洩しようがない |
| ELLE CSVに顧客情報が混入 | ELLE CSVに個人情報列がないことを確認済み。万が一追加された場合はインポート時に列ホワイトリストで弾く |
| ログに個人情報が残る | APIレスポンスの生データをログに保存しない。ログは商品ID・数量等の業務データのみ |

**リスク④: Meta広告連携（Phase 4）の特別対策**

> ⚠️ Meta広告アカウントの乗っ取り被害を踏まえ、API直接連携は**見送り**を推奨。

| 方式 | リスク | 推奨度 |
|------|-------|:---:|
| ~~Meta Marketing API 直接連携~~ | アクセストークン漏洩時に広告操作・課金が可能。乗っ取りリスク大 | **×** |
| **CSV手動エクスポート** | Meta管理画面からCSVダウンロード → システムにアップロード。APIトークン不要 | **◎** |
| Google Sheets経由 | Meta → Googleスプレッドシート（Supermetrics等）→ システムが読み取り | **○** |

**推奨: Meta広告データはCSV手動インポートまたはGoogle Sheets経由とし、Meta APIトークンをシステムに持たせない。**

#### 緊急時対応（インシデント発生時）

**APIトークン漏洩が疑われた場合:**
1. **即時無効化** — 各サービスの管理画面からトークンを無効化（1分以内に実行可能）
2. **新トークン発行** — 新しいトークンを発行し環境変数を更新
3. **アクセスログ確認** — 不正なAPIコールがなかったか各サービスのログを確認
4. **影響範囲の特定** — 読み取り専用なので、データ改ざん・金銭被害は発生しない。閲覧された可能性のあるデータ（在庫数・売上数）を特定

**キルスイッチ:**
- 管理画面に**「外部連携一時停止」ボタン**を設置
- ワンクリックで全API連携を停止し、バッチ処理も一時中断
- 停止中はCSVインポートのみで運用を継続可能

#### 監査ログ

| ログ項目 | 内容 |
|---------|------|
| API呼び出し記録 | 日時、連携先、エンドポイント、レスポンスステータス、取得件数 |
| トークン操作記録 | 発行・更新・無効化の履歴 |
| CSVインポート記録 | 日時、ファイル名、取込件数、エラー件数 |
| 異常検知 | API連続エラー、想定外のデータ量、通常時間外のアクセス |

> 監査ログは90日間保持。異常検知時はSlackに自動通知。
